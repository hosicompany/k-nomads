# Task Decomposition Command

## 사용법
이 커맨드는 복잡한 문제를 체계적으로 작은 단위로 분해합니다.

**입력**: 해결해야 할 문제 또는 기능 요구사항
**출력**: 실행 가능한 작업 단위로 분해된 계획

---

## 커맨드

**문제**: $ARGUMENT

### 1단계: 문제 이해 및 범위 정의

#### 핵심 목표
- 이 문제를 해결했을 때 달성되는 최종 상태는 무엇인가?
- 성공 기준은 무엇인가?

#### 제약사항 파악
- 기술적 제약사항
- 시간/리소스 제약사항
- 의존성 (다른 작업이 먼저 완료되어야 하는가?)

#### 영향 범위
- 수정/생성해야 하는 파일 예상
- 영향받는 컴포넌트/모듈
- 연관된 기능들

---

### 2단계: 작업 분해 (Top-down)

#### 주요 단계 식별
문제를 3-7개의 주요 단계로 나눕니다.

**예시 구조**:
1. [준비 단계] 데이터 모델 설계/수정
2. [핵심 로직] 기능 구현
3. [UI] 사용자 인터페이스 구현
4. [통합] 기존 시스템과 통합
5. [검증] 테스트 및 확인

각 주요 단계를 다음 기준으로 세분화:

#### 세부 작업 (SMART 원칙 적용)
각 주요 단계를 **Specific**, **Measurable**, **Actionable**, **Relevant**, **Time-bound** 작업으로 분해:

**주요 단계 1: [이름]**
- [ ] 작업 1.1: [구체적 동작] - 예상 시간: X분
  - 입력: ...
  - 출력: ...
  - 완료 기준: ...

- [ ] 작업 1.2: [구체적 동작] - 예상 시간: X분
  - 입력: ...
  - 출력: ...
  - 완료 기준: ...

**주요 단계 2: [이름]**
- [ ] 작업 2.1: ...
- [ ] 작업 2.2: ...

---

### 3단계: 의존성 관리

#### 작업 순서도
```
작업 1.1 → 작업 1.2
              ↓
작업 2.1 ← 작업 1.2
  ↓
작업 2.2 → 작업 3.1
```

#### 병렬 가능 작업
- [작업 A]와 [작업 B]는 동시 진행 가능
- [작업 C]는 독립적으로 먼저 수행 가능

#### 블로킹 작업 (필수 선행 작업)
- [작업 X] 완료 전까지 [작업 Y] 시작 불가

---

### 4단계: 위험 요소 및 대안

#### 잠재적 위험
- 위험 1: [설명]
  - 완화 전략: ...
  - 대안: ...

- 위험 2: [설명]
  - 완화 전략: ...
  - 대안: ...

#### 기술적 불확실성
- 불확실한 부분: [설명]
  - 조사 필요 사항: ...
  - POC 필요 여부: ...

---

### 5단계: 검증 계획

#### 단위 검증 (각 작업별)
- 작업 1.1 검증: [방법]
- 작업 1.2 검증: [방법]

#### 통합 검증 (주요 단계별)
- 단계 1 완료 후: [확인 사항]
- 단계 2 완료 후: [확인 사항]

#### 최종 검증 (전체 문제 해결)
- [ ] 기능 테스트: [체크리스트]
- [ ] 성능 테스트: [기준]
- [ ] 접근성 테스트: [기준]
- [ ] 브라우저 호환성: [확인 항목]

---

### 6단계: 실행 계획 요약

#### 우선순위 그룹
**P0 (필수, 즉시 시작)**
- [작업 목록]

**P1 (중요, 순차 진행)**
- [작업 목록]

**P2 (선택, 시간 있으면)**
- [작업 목록]

#### 예상 총 소요 시간
- 최소: X시간
- 최대: Y시간
- 예상: Z시간

#### 첫 번째 작업
**지금 바로 시작할 작업**: [작업 이름]
- 파일: [경로]
- 동작: [구체적 설명]
- 예상 시간: X분

## 체크리스트: 좋은 작업 분해인가?

### ✅ 각 작업이...
- [ ] 30분-2시간 내 완료 가능한가?
- [ ] 명확한 시작점과 끝점이 있는가?
- [ ] 완료 여부를 객관적으로 판단 가능한가?
- [ ] 하나의 파일/컴포넌트/기능에 집중하는가?
- [ ] 실행 가능한 동사로 시작하는가? (생성, 수정, 추가, 제거, 구현, 테스트)

### ✅ 전체 계획이...
- [ ] 논리적 순서를 따르는가?
- [ ] 의존성이 명확한가?
- [ ] 위험 요소를 고려했는가?
- [ ] 검증 방법이 포함되었는가?
- [ ] 누락된 단계는 없는가?

### ❌ 피해야 할 것
- [ ] "그냥 구현하기" 같은 모호한 작업
- [ ] 하루 이상 걸리는 큰 덩어리 작업
- [ ] 여러 기능을 한 번에 다루는 작업
- [ ] 검증 방법 없이 "완료" 상태로 넘어가기
- [ ] 의존성 무시하고 순서 없이 진행

## 실행 예시

### 문제: "다크 모드 기능 추가"

**1단계: 문제 이해**
- 목표: 사용자가 라이트/다크 테마를 선택하고 저장 가능
- 제약: Tailwind CSS 기반, localStorage 사용
- 영향: 모든 페이지, 모든 컴포넌트

**2단계: 작업 분해**

주요 단계:
1. 테마 상태 관리
2. UI 토글 구현
3. 스타일 적용
4. 지속성 구현

세부 작업:
- [ ] 1.1: Zustand 테마 스토어 생성 (15분)
  - 파일: `store/useThemeStore.ts`
  - 상태: theme ('light' | 'dark')
  - 액션: toggleTheme(), setTheme()

- [ ] 1.2: localStorage persist 추가 (10분)
  - persist 미들웨어 적용
  - 키: 'k-nomads-theme'

- [ ] 2.1: ThemeToggle 버튼 컴포넌트 (20분)
  - 파일: `components/ui/ThemeToggle.tsx`
  - 아이콘: 🌙/☀️
  - 클릭 시 toggleTheme() 호출

- [ ] 2.2: Header에 ThemeToggle 추가 (5분)
  - 파일: `components/layout/Header.tsx`
  - 프로필 아이콘 옆 배치

- [ ] 3.1: globals.css 다크모드 변수 (30분)
  - CSS 변수 정의
  - .dark 클래스 스타일

- [ ] 3.2: 모든 컴포넌트 다크모드 대응 (60분)
  - Tailwind dark: 클래스 추가
  - 우선순위: Header, Footer, CityCard, Button

- [ ] 4.1: HTML 클래스 동기화 (15분)
  - 파일: `app/layout.tsx`
  - useEffect로 document.documentElement.classList 업데이트

**3단계: 의존성**
```
1.1 → 1.2 → 2.1 → 2.2
              ↓
            4.1
              ↓
            3.1 → 3.2
```

**4단계: 위험**
- 위험: 초기 로드 시 깜빡임
  - 완화: script 태그로 SSR 시점 클래스 적용

**5단계: 검증**
- 토글 클릭 시 즉시 반영
- 새로고침 시 테마 유지
- 모든 페이지 일관성

**첫 작업**: `store/useThemeStore.ts` 생성
